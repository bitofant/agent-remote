# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Everything in CLAUDE.md must be extremely terse: bulleted lists, not paragraphs, as concise and token-efficient as possible.**

**Keep this file correct: update it when details change, and add genuinely important architectural decisions as they're made.**

**Code comments must be extremely terse too: short one-liners explaining *why*, never restating the code. No prose blocks, no redundant JSDoc.**

## Project state

- Scaffolded. Working vertical slice: launch Claude Code/pi sessions, stream live to xterm in the browser, type back, switch between concurrent sessions.
- TypeScript throughout. Tests use **Vitest** (`npm test`), co-located `*.test.ts` next to source, Node environment (`vitest.config.ts`). First coverage is the pure shared logic (`shared/chat.test.ts` reducer, `shared/render.test.ts`) — no DOM, no processes, no tokens. Test files are excluded from `npm run typecheck` (both tsconfigs) so that gate stays scoped to shipping code; Vitest runs them. Component tests (jsdom + Testing Library) and live smoke scripts layer on top later.
- **Prefer TDD when adding a new harness surface or normalized message type** — i.e. a new `ChatEvent` / `ChatAction` / `ChatUiRequest` kind, an adapter mapping a fresh SDK/harness signal, or a new agent interaction flow (permissions, dialogs, resume, compaction, plan-mode/`ExitPlanMode`, model/mode switches). These have a clean *observable backend contract* (the emitted events / folded `ChatState`) that a token-free `claude-local` `*.e2e.test.ts` can pin. Order: **draft the test first** against the intended contract → **implement** the adapter/protocol → **run it live and adjust the test** to what the real harness actually does (e.g. an empty `plan` field, messages the SDK does/doesn't replay) → **only then build the frontend**. Keep the deterministic assertion (our event surfacing) as the hard gate and any model-behavior check (recall, verbosity) as a softer secondary one.

## Commands

- `npm run dev` — single-process dev server (`tsx watch server/index.ts --dev`).
- `npm run build` — production frontend build to `dist/web` (Vite).
- `npm start` — run server serving the prebuilt `dist/web`.
- `npm run typecheck` — `tsc --noEmit` for web (`tsconfig.json`) + server (`tsconfig.server.json`).
- `npm test` — Vitest run (once, pure/fast — no processes/tokens); `npm run test:watch` for the watch loop. Excludes `*.e2e.test.ts`.
- `npm run test:e2e` — live end-to-end tests (`*.e2e.test.ts`, `vitest.e2e.config.ts`) that drive the real `claude-local` harness against vLLM; self-skip when claude-local is disabled/unreachable. Kept out of `npm test` (needs a running endpoint).
- `npm run chat-log-report` — offline chat-render-log diagnostics (see chat render log below).
- Requires `config.json` (run `./config-gen.sh`); the agent CLIs (`claude`, `pi`) must be on `PATH`.
- Server is **never compiled** — `npm start` runs `tsx server/index.ts` directly. Only the frontend is built (`dist/web`).

## Deployment (systemd user service)

- **⚠️ NEVER run `./restart.sh`, `./rebuild.sh`, `./stop.sh`, or any `systemctl --user restart/stop agent-remote` yourself.** The agent (you) runs *inside* this application — restarting/stopping/rebuilding the service kills all live sessions, including your own. When a change needs to be picked up, **ask the user to run `./restart.sh`** themselves; never do it (or the rebuild) on their behalf.
- `./install-service.sh` — one-time: writes/enables `~/.config/systemd/user/agent-remote.service` (runs `npm start`), builds `dist/web` if missing, enables linger. User service (not system): agent CLIs live in per-user paths.
- `./start.sh` / `./stop.sh` / `./restart.sh` wrap `systemctl --user` as the canonical prod runner. `./restart.sh` rebuilds frontend then restarts.
- `./start.sh dev` is the exception: runs the `tsx watch` HMR server directly (pidfile + `setsid`, not systemd). `./stop.sh` prioritizes that pidfile if present, else stops the service.
- `./rebuild.sh` builds frontend only. Frontend change → rebuild + restart; server-only change → plain `systemctl --user restart agent-remote` (no build needed).
- **Restart resilience** (restart.sh used to leave the service dead; three compounding causes, all fixed — don't regress any):
  - `rebuild.sh` **stages + atomically swaps** (`vite build --outDir dist/web.next` → two `mv`s). Vite's `emptyOutDir` used to wipe `dist/web` under the live server for the whole build.
  - `serveStatic` (`index.ts`) **try/catches the read** → 503, and the server has `uncaughtException`/`unhandledRejection` log-and-continue handlers. A missing `index.html` mid-rebuild threw ENOENT out of an async handler and killed the process (and every live session). The SPA fallback path is not `existsSync`-checked, so it can always vanish under us.
  - `restart.sh` runs the rebuild+restart in a **transient unit** (`systemd-run --user --collect --unit=agent-remote-restart`) so it's outside the cgroup systemd is tearing down — the caller is normally an agent session *inside* the service, so an inline build gets killed half-way. It also verifies the unit came back and re-`start`s it if not. Falls back to inline when systemd-run/the unit is absent. (This is why `nohup ./restart.sh` used to be needed; it isn't now.)
  - Unit has `Restart=always` + `StartLimitIntervalSec=0` (default 5-starts/10s budget let a crash-loop wedge it dead permanently) + `TimeoutStopSec=20`.

## Layout

- `shared/protocol.ts` — WS message + session types, shared by both sides. Harness-agnostic. Also `CommandListing` (the `/api/commands` response shape), `SessionEvent` (command-start/end + cwd events), `FileEntry`/`DirListing`/`FileContent` (the file-editor `/api/files` + `/api/file` shapes), and the normalized chat schema (`SessionUi`, `ChatState`/`ChatMessage`/`ChatPart` — incl. the `image` part variant, `ChatEvent`, `ChatAction` — `prompt` carries optional `images:ChatImageRef[]`, `ChatUiRequest`/`ChatUiOption`, `ChatImageRef`, `ChatCapabilities`/`RewindPreview`). **Card options are structured** (`ChatUiOption {value,label,detail?,intent?}`): `value` is the stable id round-tripped in `ui-response.value` and matched by the adapter, `label`/`detail` are display-only (so a harness can enrich button text without breaking the decode), and `intent` (`accept`/`always`/`reject`/`cancel`) carries the semantics so `ChatView` and `assistant.ts` never pattern-match on label strings (AI-mode picks `accept`, never `always`).
- `shared/chat.ts` — `applyChatEvent` reducer folding `ChatEvent`s into `ChatState`; run identically by server (replayable per-session state) and client (live updates). Caps: 200 messages, 20k/tool output, 20 notices. The only *destructive* fold is `rewind` (see below) — everything else appends/patches.
- `shared/render.ts` — single source of truth for turning a `ChatPart`/`ChatMessage` into displayed HTML (`renderPart`/`renderMessage`, plus the `md`/`escapeHtml`/`argsPreview`/`toolGlyph`/`truncate` primitives). `ChatView.tsx` imports the primitives so the UI can't drift from what's logged; `server/chatLog.ts` calls `renderMessage` to capture what's shown. Imports `marked` — keep it imported only by `ChatView` on the web side so it stays in the lazy chunk.
  - **Tool-call display** is driven by `toolView(part)` (field-driven, harness-agnostic — covers claude's `Edit`/`Read`/`Write`/`Bash` and pi's lowercase `read`/`write`/`bash` by looking at `file_path`/`path`, `command`, `old_string`/`new_string`, `content`, not tool names): returns a `{primary, secondary?, body}` display model. Summary shows a legible subject (`shortenPath` → `…/dir/file.ts`, or the command) not raw JSON; body is a red/green line diff for edits (`lineDiff`, minimal LCS), a code block for Write/Bash content, path+range for Read, or pretty JSON for unknown tools. Both `renderPart` (HTML) and `ChatView`'s `ToolPart` (JSX) consume `toolView` so they can't drift. Tool bodies use `white-space: pre` + horizontal scroll (mobile pans, never wraps per-column). **An assistant turn renders as a *column of bubbles*, not one** (`groupParts` in `render.ts`, consumed by both `ChatView`'s `Bubble` and `renderMessage`): consecutive prose parts share a bubble, each tool call is its own (`.chat-tool.standalone` — `--panel` fill + `--r-lg`, i.e. bubble weight, with `overflow:hidden` clipping its full-bleed bodies). A turn is nearly always all prose or all tool, and the old single-bubble layout made the common tool-only turn a raised card inset inside a near-empty bubble; a mixed turn now just yields several bubbles. Nested `.chat-tool` (raised card, `--r-sm`) survives for the permission card, which is why `standalone` is a modifier rather than a change to the base rule. **This is presentation only** — grouping happens at render time, never in the reducer, since `ChatMessage.id` is load-bearing for rewind (`promptIds`), `AssistantTrace.anchorMessageId`, the `chat_render_log` key, and the streaming→finalized handoff. Prose groups key off their first part's index, tool groups off `toolId` so `<details>` open state survives a growing turn. Empty `thinking` parts (claude never streams reasoning) render as a transient pulsing "Thinking…" label and are stripped by the `shared/chat.ts` reducer (`dropEmptyThinking`) once the next part starts or the turn ends.
- `server/` — Node backend. `config.ts` (loads `config.json`), `auth.ts` (password/cookie auth — see below), `llm.ts` (optional LLM assist — see below), `suggestions.ts` (harness-agnostic synthesized next-prompt suggestions — see below), `autopr.ts`/`prAgent.ts`/`git.ts` (the auto-PR capability — see below), `adapters/` (harness boundary, incl. `shell-integration/` injected rc scripts), `sessions/manager.ts` (PTY/streaming/lifecycle + session-event fan-out, harness-agnostic), `commands.ts` (lists cwd executables + `$PATH` + shell aliases + recent/frequent commands from the DB command log; PATH/alias cached 30s), `files.ts` (file-editor backend: list subfolders / read / write, every path confined to a folder root), `browse.ts` (add-folder picker backend — see below), `chatLog.ts` (chat render log capture — see below), `paths.ts` (`expandHome` — see below), `db.ts` (SQLite: folders, users, auth sessions, command log, resumable chat sessions, chat render log), `index.ts` (HTTP + WS + dev Vite).
- **Session ↔ folder membership:** `SessionInfo.folder` (launch cwd, fixed for the session's life) is the *only* thing sessions are grouped by — `App.tsx`'s `sessionsInFolder`, the auto-select-new-session effect, `manager.sessionFolder` (folder-recency bumps), `chat_sessions.folder`. **`SessionInfo.cwd` is live and drifts with every `cd`** (shell integration) and is display/logging only (`sessionCwd` → command log, session-row subtitle). Grouping by `cwd` was a real bug: `cd` out of the launch folder made the session vanish from the UI (its cwd matched no known folder, while it stayed running and mounted), then re-attach itself to whatever folder was *added later* at that path. Membership must never depend on mutable state. The active-tab pin (`activeSession[folder]`) is likewise validated against the folder's own tabs before use — terminals are all mounted at once and shown purely on an id match, so a foreign pin paints another folder's session over an empty tab list.
- **Folder path normalization (`server/paths.ts`):** a folder path is an *identity* (the `folders` primary key, and what `SessionInfo.folder` is compared against to group a session under its folder), so it has exactly one spelling: `normalizeFolder` = `expandHome` + a guaranteed trailing slash. Two spellings of one folder = two list entries that drift apart, each with its own sessions/command history.
  - `expandHome` expands a leading `~`/`~/…` (never `~user/…`, needs a passwd lookup). `~` is shell syntax — Node's `fs`/`spawn` treat it as a literal directory name, so a folder typed as `~/src/foo` never resolves (nothing to do with the service user: it's a systemd *user* service, so `HOME` is already the installing user's).
  - Applied at the WS entry points in `index.ts` (`start` cwd, `addFolder`, `removeFolder`) so the allowlist / session cwd / `/api` cwd params see one form — **and again inside `db.ts`'s `upsertFolder`/`removeFolder`**. The DB one is load-bearing, not belt-and-braces: one un-normalized write anywhere forks the folder (this is exactly how a `~` row bred a duplicate — opening it upserted the *expanded* session cwd as a second row). **Normalize at the persistence boundary, never per call site.**
  - `manager.ts` normalizes the shell-integration `cwd` event too — a shell reports `/x/y` where the folder key is `/x/y/`, which would drop a session out of its own folder tab.
  - `db.ts` `migrateFolderPaths()` (runs at import, idempotent) folds legacy rows into canonical form: merges into an existing canonical row keeping the newer `last_used_at`, and for `~` rows re-points `chat_sessions.folder` / `commands.cwd` / `chat_render_log.cwd` (slash-only fixes don't re-point — those columns hold live cwds, incl. subdirectories, whose trailing slash is their own).
  - Client-side, `submitNewFolder` never predicts the stored path: it defers selection (`pendingFolderSelect`) to the next `folders` broadcast, where the add sorts first.
  - **Display is the other half:** storage is canonical/absolute, but the UI shows paths home-relative (`~/src/x/`). The `folders` server message carries `home` (server `$HOME`) alongside the list — the browser can't know it — and `web/paths.ts` `displayPath(path, home)` renders it (folder list + folder header; `title=` keeps the absolute path). Home *itself* is the exception — it stays absolute (`~/` alone names nothing) and `folderName(path, home)` labels it "home" rather than the account name. Display only: every path sent back to the server is the stored one. Pure coverage `web/paths.test.ts`.
- **Add folder (folder picker):** the sidebar's "+ Add" opens `FolderPicker.tsx`, a modal filesystem browser (reuses the `.resume-*` dialog shell) mounted at app level in `App.tsx` — adding a folder must work with none open. **The text field is the source of truth; the tree is a view of it** (ancestors auto-expanded, best prefix match highlighted), and every tree interaction writes back into the field, so typing/Tab/tap all converge on one string. Typed text splits at the last `/` into a directory (listed) + a partial name (prefix-filters its subfolders, case-exact first); ↑/↓ move the highlight, Tab completes it into the field with a trailing `/`, Enter adds (or, when the partial isn't a real folder, completes instead — Add is disabled and "No such folder." shown only once the parent listing proves it missing). Path text logic is pure in `web/folderPath.ts` (`splitTyped`/`toAbsDir`/`toTyped`/`parentOf`/`rootFor`/`chainFrom`/`matchEntries`, tested in `folderPath.test.ts`): display keeps `~/` (here home itself collapses too, unlike `displayPath`) while tree keys and requests are canonical absolute paths, and the tree roots at home when the path is inside it (else `/`). Backend is `GET /api/browse?path=` → `server/browse.ts` `browseDirs` (auth'd; `~`/empty = home; directory *names* only, symlinked dirs followed, 1000-entry cap with `truncated`, fs errors mapped to readable text). Deliberately **not** folder-allowlisted, unlike `/api/files` — you're picking a folder that isn't known yet, and typing a path by hand always reached just as far. Submitting still sends the raw text: the server normalizes it (`normalizeFolder`) and `pendingFolderSelect` adopts whatever it stored.
- `web/` — React app. `client.ts` (WS client, per-session output buffering + per-session `ChatState`, sticky Ctrl modifier applied in `input()`), `auth.ts` (client-side auth helpers), `Login.tsx` (login/signup gate), `TerminalView.tsx` (xterm per session), `ChatView.tsx` (chat-bubble view for `ui:"chat"` sessions, lazy-loaded, bundles `marked`), `FileEditor.tsx` (the file-editor tab: file picker + CodeMirror, lazy-loaded), `App.tsx` (workspace + mobile keyboard key-bar + editor-tab bookkeeping + AI-assistant mode toggle), `CommandBuilder.tsx` (the `./` command-builder dialog), `FolderPicker.tsx` + `folderPath.ts` (the add-folder browser — see below), `commandCatalog.ts` (static well-known-command subcommand/flag data + curated common-command list), `styles.css`. Becoming the active tab focuses that session's input (xterm / chat composer) so it's typeable at once; while an exited session is active, Enter/Escape trigger "Close session" (`App.tsx` window keydown, suppressed while a dialog is open).
- **Last view (server-persisted, per user):** which folder + tab you were on survives a reload and follows you across devices. `ViewState {folder, sessionId}` (`shared/protocol.ts`) ↔ `user_views` table (one row per user, folder normalized in `setUserView` like every other folder column) ↔ `GET/PUT /api/view` (auth'd, keyed by `authedUser`). **Load-time only, deliberately not over `/ws`** — a live broadcast would yank an open laptop tab around when you tap something on your phone. `App.tsx`: fetch on mount → `storedView` ref; a one-shot restore effect waits for `viewFetched` + `snapshotSeen` (the first WS `sessions` message; the server sends `folders` before it) so ids can be validated. **`client.onSessions`/`onFolders` replay their current value synchronously on subscribe**, so the connect effect's `replaying` flag ignores that first (empty) call — counting it as the snapshot made the restore run against an empty folder list and silently fall through to the default every time. The restore is also ordered *after* the auto-select-new-session effect, which treats the whole first batch as new and would otherwise win. `viewRestored` gates both the "default to most-recent folder" effect (else it races the stored folder) and the debounced save (else the default overwrites what was stored). Stale ids just fall back to the folder's default tab — sessions die, and editor tabs are client-only so their ids never survive a reload.
- **Chat sessions (pi + claude):** `SessionInfo.ui` is `"terminal" | "chat"`, declared by the adapter. Two adapter shapes drive chat, both harness-confined; the manager just folds their `ChatEvent`s into per-session `ChatState`:
  - **`createChatTranslator()` (pi)** — manager spawns the agent **piped, no PTY** (`child_process.spawn`); the `ChatTranslator` maps wire format ↔ schema (`push(stdout) → ChatEvent[]`, `encode(ChatAction) → stdin bytes + synthetic events`). pi runs `pi --mode rpc` (JSONL, manual `\n` framing, never readline — U+2028/29). ALL pi vocabulary in `adapters/pi.ts`.
  - **`createChatSession()` (claude)** — the adapter owns the process/SDK and exposes `start(handlers)`/`action(ChatAction)`/`close()`; the manager drives that interface (no child/translator). `adapters/claude.ts` wraps the **Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk`, `query()` with a pushable async-generator prompt stream). This is what buys **feature parity with the TUI**: `canUseTool` → permission cards (`ui-request` select Allow/Deny, plus "Always allow" when the SDK supplies `suggestions`; resolved by `ui-response`). **Always-allow:** the SDK's `suggestions` are *alternatives* (the TUI's separate buttons), not a bundle — a Bash call yields an `addRules` **plus** an `addDirectories` **plus** a `setMode`, so `alwaysAllowUpdates()` returns only the rule ones as `updatedPermissions` (sending the lot would also flip the session to acceptEdits and grant a directory off one click). The CLI persists them at its own suggested `destination` — in practice `localSettings`, i.e. it creates/updates the project's `.claude/settings.local.json` (`{"permissions":{"allow":["Bash(touch notes.txt)"]}}`) — so the rule survives restarts; we never write that file ourselves. `describeSuggestions()` renders the rule + destination as the option's `detail` (`Bash(touch notes.txt) · saved to local settings`) so the button names what it grants instead of being a blank cheque. Edit tools instead get "Allow all edits" (session-scoped `acceptEdits` flip, no rule). Pure coverage `claude-permissions.test.ts`; live `claude-permission.e2e.test.ts` asserts the option shape, the detail text, and that the settings file really gains the rule. The card carries the tool as `ChatUiRequest.tool` (`{name, args}`), NOT a pre-summarized `message` string, so `ChatView` renders it through the shared `toolView` (same diff/code/path view as the transcript, expanded) instead of raw arg JSON. **Plan mode:** in `permissionMode:"plan"` Claude drafts a plan and calls the `ExitPlanMode` tool instead of executing; the adapter special-cases it into a distinct `ui-request` of `kind:"plan"` (the plan markdown rides in `message`, options `["Accept plan","Keep planning"]`). Accept → allow the tool (exits plan mode) **and** `setPermissionMode("acceptEdits")` so the follow-through auto-accepts edits; Keep planning → deny the tool with the typed instructions as the message (model stays in plan mode and revises). `ChatView` renders the plan as a bordered markdown card (`kind:"plan"`) with an "Accept plan & auto-accept edits" button + a refine-instructions box; the LLM auto-decider ignores `plan` (accepting a plan is always human-driven). `onUserDialog`+`supportedDialogKinds:["permission_ask_user_question"]` → the **AskUserQuestion** tool as a structured `ui-request` of `kind:"questions"` (1–4 questions, each 2–4 label+description options, `multiSelect`) instead of a raw permission card; the answers ride back as a PermissionResult `updatedInput.answers` (question text → chosen label(s), multi joined `", "`), mirroring the TUI. Other dialog kinds aren't declared → CLI applies its default, `setModel`/`supportedModels` → model switcher (**menu policy in `adapters/model-menu.ts`**, pure/tested: `menuLabel` appends the resolved version to alias rows, `pruneToLatest`+`sortModels` curate latest-per-family, `current` derived from the shown rows. **A bracketed suffix is a variant, not a version** — the enterprise catalog lists `claude-opus-4-8` *and* `claude-opus-4-8[1m]` (same model, 1M context, drawn from usage credits), so `isVariant` gives it its own pruning group (both survive; each prunes its own older versions), strips the tag before parsing the version (else `claude-sonnet-5[1m]` reads as 5.1), and sorts it after its plain row. **`pickDefault(menu, DEFAULT_MODELS)` (not `includes()`) picks the starting model** from an ordered alias preference — today `["opusplan","opus"]`, i.e. Opus Plan Mode where the catalog offers it (work/enterprise), else plain Opus (private). Ranking: earlier alias wins outright → exact alias row / versioned id of that family / mere substring → plain before `[1m]` → highest version. A substring scan can't express this (`"opusplan".includes("opus")`), which is why it matched whichever sorted first. Behaviour aliases like `opusplan` are unversioned, so pruning always keeps them in the menu. **`SEED_MODEL` (`"opus"`) is separate**: `query({model})` is seeded before the catalog is known, so `loadControlInfo` then `setModel`s to the resolved pick when it differs — otherwise the header would claim Opus Plan Mode while the CLI ran plain Opus (behavioural, not cosmetic). That switch has its own try/catch so a catalog refusing it still yields a model list + slash commands and keeps reporting what's actually running; the pick is stored on `this.model` so a rewind relaunch keeps it. No filtered/unfiltered UI toggle — showing both the plain and `[1m]` rows is the whole point), `setPermissionMode` → mode toggle (a fixed `modes` event lists Default/Plan/Allow-all-edits/Auto; `set-mode` action → `setPermissionMode`), `supportedCommands` → slash-command palette (all fetched eagerly on start, before the first prompt). SDK message mapping mirrors the raw stream-json shapes (stream_event deltas → part events; `input_json_delta` accumulates tool args, emitted at `content_block_stop`; `user` tool_result → `tool-end`; `result` → busy false). **Compaction:** the SDK `system`/`compact_boundary` message (manual `/compact` or auto when the window fills) → an info `notice` (`Compacted context (pre → post tokens) [manual|auto]`) so the transcript marks the boundary instead of silently swapping history for a summary; a `system`/`status` with `compact_result:"failed"` → an error notice. `permissionMode: "default"` = auto-allow read-only, prompt (via `canUseTool`) for the rest. Abort = `query.interrupt()`. **Next-prompt suggestions:** `promptSuggestions:true` on `query()` makes the CLI emit a `prompt_suggestion` SDK message after each turn (never the first) with a predicted next user prompt → mapped to a `prompt-suggestion` `ChatEvent` (wrapped as a **single-element** list — the schema `ChatState.promptSuggestions` is `string[]`; Claude only ever emits one) → folded into `ChatState.promptSuggestions` (cleared on the next `user-message`). `ChatView` shows them as dashed chips above the composer (idle + empty composer only; wrap horizontally, capped at two rows); a tap prefills the composer with the full prompt for review (never auto-sends). The suggestion is a *secondary CLI model call* — works against the real Anthropic endpoint but the **claude-local** harness emits none (small model errors on it; SDK suppresses suggestions after API errors), so the deterministic mapping/fold is pinned by pure reducer tests and the live e2e only best-effort-probes it. Claude declares `HarnessAdapter.nativePromptSuggestions:true` so the generic synthesizer (below) skips it; harnesses without native suggestions (pi) get 1–3 synthesized server-side into the same `ChatState.promptSuggestions`.
  - **Billing:** claude stays flat-rate subscription — the SDK drives the Claude Code CLI on the user's OAuth creds. Never set `ANTHROPIC_API_KEY` or `--bare` (forces metered API) **on the production `claude` harness**. Verified on subscription.
  - **CLI binary (local vs bundled):** the Agent SDK ships its *own* version-pinned native `claude` (an optional dep, `@anthropic-ai/claude-agent-sdk-<platform>`) and spawns it unless `pathToClaudeCodeExecutable` is set. That bundled copy can lag the CLI the user installed, so its **model catalog trails** (symptom: `/model` shows fewer models in the web UI than the standalone TUI — e.g. no "Opus 5"). `createClaudeAdapter` therefore resolves the harness's `cfg.command` (default `claude`) on `$PATH` **once at startup** via `resolveLocalCli()` (returns an absolute native-binary path; rejects `.js`/`.mjs`/… so the SDK spawns it directly, not via node) and threads it to `ClaudeChatSession` → `query({pathToClaudeCodeExecutable})`; missing → SDK falls back to its bundled binary (logged either way). Keep the SDK version bumped too so its message-mapping protocol stays compatible with a newer local CLI. Pure coverage: `claude-cli.test.ts`.

- **Resume (chat sessions):** harness-agnostic via an opaque "resume key". `SessionOptions.resume` (input) → adapter restores prior state; `ChatSessionHandlers.onResumable(key)` (output) → manager persists it. Both **claude** and **pi** implement resume; **terminal** ignores it. Two mechanisms by adapter shape:
  - **claude (ChatSession)** — the adapter owns identity: passes `resume` to `query()` (restores the model's context) and reports the SDK `session_id` from the `system`/`init` message via `onResumable`.
  - **pi (ChatTranslator)** — the *manager* owns identity (the translator contract has no session concept). The adapter sets `resumable:true`; in `startChat` the manager mints a stable id (`opts.resume ?? randomUUID()`), threads it into `invocation()` via `SessionOptions.resume`, and reports it via `onResumable` (fresh and resumed alike). pi's `invocation` turns it into `--session-id <id>` (creates if missing, reloads+restores context if present — same flag both ways). pi's RPC stream, like claude's SDK, does NOT replay prior turns on reload, so the adapter rebuilds the transcript from pi's on-disk session JSONL (`~/.pi/agent/sessions/<mangled-cwd>/*_<id>.jsonl`; `mangleCwd` = `--`+segments joined by `-`+`--`, with a full-scan fallback since ids are UUIDs) via the optional `ChatTranslator.replayHistory(opts)` hook — the manager calls it on resume and folds the returned events (`message` lines → user/assistant/toolResult → same ChatEvent vocabulary) into `ChatState` before the first new prompt. Best-effort: unreadable history yields an empty transcript (context is still restored). All pi session-file knowledge stays in `adapters/pi.ts`.
  - (claude gotcha) The SDK does NOT stream the prior conversation back on resume (nothing is emitted until the first new prompt, and even then only the new turn — no `isReplay` messages). So the adapter rebuilds the visible transcript itself in `replayHistory()` by reading the on-disk JSONL via the SDK's `getSessionMessages(sessionId, { dir: cwd })`, folding those whole messages through the same `replayAssistantMessage`/`replayUserMessage`/`handleToolResults` helpers (same ChatEvent vocabulary). The `streamedThisTurn` flag (set on stream `message_start`, cleared on `result`) still guards live delta-built turns against the SDK's redundant whole-message echo; the `isReplay` branch in `handleMessage` is now a vestigial safety net (the SDK doesn't send those). `db.ts` `chat_sessions` table (keyed by resume key + folder, title = first user prompt) survives restarts; `index.ts`'s server-global subscriber persists on `onResumable`/first `user-message`. `GET/DELETE /api/resumable?cwd=|key=` (auth'd + folder-allowlisted) list/forget; the list hides currently-live keys (`manager.liveResumeKeys()`). UI: resume is triggered from **`/resume` in `ChatView`'s slash-command menu** (mirrors the CLI), shown when the folder has resumable sessions. `/resume` is a **client-only** menu entry (not a harness `state.commands` command): `ChatView` takes `canResume`/`onResume` props; picking it calls `onResume` (not `insertCommand`), and `send()` intercepts a `/resume` draft the same way (Tab-completing it then Enter opens the picker instead of prompting the harness). The dialog state itself stays folder-level in `Workspace` (`resumable`/`resumeDialogOpen`), so `onResume={() => setResumeDialogOpen(true)}`. It opens a modal dialog listing the folder's resumable sessions **filtered to the active chat tab's harness** (`resumableForActive` in `App.tsx` — resuming a claude session in a pi tab, or vice-versa, is nonsense; `canResume` is likewise per-harness); picking one calls `client.start(harnessId, folder, resumeKey)` and closes the dialog, `×` forgets one. Reachable only when a chat tab is active (no standalone/sidebar entry).
- **Composer draft (server-side, harness-agnostic):** the unsent prompt lives in `ChatState.draft`, so a reload / folder detour / other device doesn't lose half-written text (the chat analogue of a terminal's unsubmitted line sitting in the PTY — terminals need nothing). `set-draft` `ChatAction` → handled by `manager.ts` itself like `set-assistant` (never an adapter) → `draft` `ChatEvent` → reducer. Text only; attachments stay client-side. Not persisted to SQLite — a server restart kills the session anyway.
  - Sending consumes it: the manager clears the draft on **every** `prompt` action, unconditionally (the `if (session.chat?.draft)` around it only skips a no-op broadcast — the sender normally cleared it already). A prompt sent is a draft spent; don't reintroduce a conditional clear (an earlier prefix-match rule tried to protect text typed *after* Send, since `index.ts` resolves prompt images async and so applies an image prompt *after* later `set-draft`s — that window is worth less than the simple rule, and `ChatView` keeps the local draft authoritative anyway).
  - `ChatView` keeps the local `draft` authoritative for the caret and syncs on a 300ms debounce (+ an unmount flush + an explicit clear on send). Two guards make the echo safe, and both were real bugs: it adopts a server value only after the server has **acked our latest push** (`acked` ref — an in-flight echo would otherwise resurrect a just-sent prompt), and only when the composer is **empty or unfocused** (an outright "never while focused" rule broke the main case: on a reload the snapshot arrives *after* mount, by which time the composer is already focused). `index.ts`'s chat-render-log subscriber skips `draft` events alongside `part-delta`/`tool-update` — they touch no message.
- **Rewind (claude only):** jump the conversation back to an earlier **user** prompt — it and everything after it leave the transcript *and* the model's context; the agent is interrupted; the prompt goes back into the composer for re-sending. Gated by `ChatState.capabilities` (`ChatCapabilities {rewind?, rewindFiles?}`, a `capabilities` event emitted at session start), so pi shows none of it and needs no changes. **Manager/`index.ts` are untouched** — `rewind`/`rewind-preview` are `ChatAction`s that pass straight through to `chatSession.action`, and the adapter emits the resulting `rewind`/`rewind-preview` events itself.
  - **Message identity** is the crux: `ChatState` user-message ids are `randomUUID()`, unrelated to SDK transcript uuids, so `ClaudeChatSession` maps them itself — `promptIds` (ordered ids of every `user-message` it emitted, live + replayed) plus `promptUuids` (exact map). Exact uuids come from `replayHistory` (`m.uuid`) and, live, from the CLI's **echo** of our prompt in `handleMessage` `case "user"` (`msg.uuid`, paired with the oldest unpaired prompt; prose distinguishes it from tool_result-only messages). `promptUuid()` falls back to **position** among the transcript's prose user entries when the exact uuid is unknown — which is the normal path after a rewind, since `forkSession` remaps every uuid (hence `promptUuids.clear()` on relaunch). The e2e test rewinds twice specifically to cover that fallback.
  - **Mechanism:** no `Query` control request truncates history, so a rewind is a **relaunch**: `q.interrupt()` → optional `q.rewindFiles(uuid)` (gated on `enableFileCheckpointing:true`, now always set; must run on the *live* query — forks carry no undo history) → `forkSession(sessionId, {dir, upToMessageId: <entry before the prompt>})` → `teardown()` → `launch({resume: forkId, restart: true})`. `start()` was split into `start()` + `launch()`; `restart` skips `replayHistory` (clients keep their truncated transcript) and `loadControlInfo` (would reset the model selection). Model/mode are tracked on the instance so the relaunch keeps the user's picks. A **generation counter** (bumped on relaunch, compared in `consume`) makes the superseded query's abort unwind quietly instead of emitting an error notice and firing `onExit` (which would mark the session exited).
  - Forking means the **pre-rewind conversation stays resumable** (it reappears in `/api/resumable` once it's no longer live). **The CLI only emits `system`/`init` once a prompt is pushed** — so `sessionId` (the fork target) can't wait on it: `launch()` adopts `opts.resume` immediately, and the rewind adopts the fork id (`sessionId` + `onResumable(forkId)`) right after relaunching. Deriving it from `init` alone made *resume → rewind before the first prompt* fail with "session not ready" (the common case: reopen a tab, undo the last turn) and left the stale key persisted; both are pinned by e2e tests.
  - **UI** (`ChatView.tsx`, all per-session — unlike `/resume` nothing is lifted into `App.tsx`): a faded `↺` button left of every user bubble (`Bubble` gains `onRewind`; the bubble is wrapped in `.chat-turn.user`, which takes over its flex sizing — `.chat-rewind` is `opacity:.3` not `0`, so touch can reach it) and a client-only `/rewind` slash command opening a picker of prior prompts. Both land in the same `RewindConfirm` dialog (`.resume-*` shell + `.rewind-dialog`), which fires `rewind-preview` on open and shows the dry run beside an "also restore files" checkbox. Confirming prefills the composer (text + image refs) *before* dispatching `rewind`, since the truncation drops the message. The client-only-command hack generalized: menu entries carry an optional `run()` (`/resume` and `/rewind`) instead of `/resume`'s old `resume?: boolean` flag; `send()` intercepts both bare drafts.

- **Theming:** the palette is **12 CSS vars + a 3-step radius scale in `styles.css`'s `:root`** and nothing else — every color in the app resolves to one (`--bg`/`--panel`/`--raised`, `--text`/`--muted`, `--accent`/`--on-accent`, `--success`/`--warning`/`--danger`/`--danger-hover`/`--on-danger`).   - **Elevation, not outlines** (the settled design idiom — don't regress it). **There is no border colour in the palette at all**: surfaces separate by three background steps, `--bg` < `--panel` < `--raised`, plus a shadow on floating things. **Nested content must rise, never sink** — a `--bg` fill inside a `--panel` card is the "sunken well" bug that made the old design read as dated; it kept recurring in *state* rules (hover/active/selected), so those use an accent tint (`color-mix(… var(--accent) 10–20%, var(--raised))`) rather than a darker fill. The one legitimate darkening is a momentary `:active` press.
  - The only surviving `border` declarations are **signal, never structure**: `.chat-request`'s accent ring (it blocks the turn), `.chat-plan`'s + `.chat-md blockquote`'s 3px left edge, `.assistant-warning`/`.chat-usage-plan`'s accent/danger rings, `.status-dot.editor`, and the spinner. Anything separating two same-coloured surfaces was replaced by an elevation step: dialog heads/feet (`.resume-dialog-head`, `.cmd-head`, `.cmd-foot`, `.editor-head`) went `--raised`, `.chat-commands` went `--raised` + an upward shadow, `.chat-tool-output` took a 5% `--text` tint. **Adding a divider is the wrong reflex — change the elevation instead.**
  - **Controls are filled, never outlined.** Every button/input/select/textarea/list-row is a `--raised` fill with no border. **Removing a `border` declaration from a control is not the same as having no border** — the UA stylesheet falls back to `border-style: outset`, i.e. a Windows-98 bevel. A base `button,input,select,textarea { border: none }` reset makes borderless the floor; never rely on merely deleting a rule. `select` additionally needs `appearance: none` (it otherwise draws native bevelled chrome and ignores background/border), which costs the dropdown arrow — redrawn by `.chat-model::after` as a **mask** filled with `var(--muted)` so it follows the palette (a `background-image` SVG would hardcode the colour, and a `background:` shorthand on the select would wipe it). This means **`--border` can no longer carry focus** — the old `border-color: var(--accent)` focus idiom (23 rules) was replaced by: `:focus` → a `box-shadow` ring (`0 0 0 2px` accent color-mix; a ring can't shift layout the way a border can), `:hover` → a 10% accent tint, `.active`/`.selected` → a 20% tint. **Any new control must keep a non-border focus indicator** — five rules pair `outline:none` with a ring and would go invisible if the ring were dropped.
  - **Radius scale is `--r-sm`/`--r-md`/`--r-lg` (4/8/12px).** Nested boxes must stay **concentric**: `inner = outer − padding`, so `--r-lg` wrapping 8px of padding takes `--r-sm` inside. Off-scale values make curves look non-parallel — the original bug was `--r-md` (8) nested inside a 12px bubble with 8px padding, where 4 was required. `.chat-request`'s padding is 8px 10px specifically to keep its nested `.chat-tool` concentric (the permission card is now the *only* nested tool — in the transcript a tool call is its own bubble at `--r-lg`).
  - `web/theme.ts` is the palette as data + `applyTheme`/`resetTheme`/`serializeTheme` + an `onThemeChange` pub-sub. The pub-sub exists for **xterm**, which takes colors as a JS object and can't follow CSS vars: `TerminalView` seeds `theme: xtermTheme()` and re-pushes on change (it used to hardcode a second copy of `--bg`/`--text`, which silently drifted).
  - `web/ThemeEditor.tsx` is a dev overlay: swatch + hex per color var (px slider for the `kind:"length"` radius vars), live-applied to `document.documentElement`, with a paste-ready `:root` block + Copy button (that's the export path — palettes ship by pasting into `styles.css`). Gated on the URL hash `#theme`, **not** `import.meta.env.DEV`, since the app normally runs as the prod systemd service — that's where the real sessions worth restyling are. Lazy-chunked; a `localStorage` draft (`DRAFT_KEY`, restored in `main.tsx` pre-render) keeps a palette across reloads but is a scratch buffer, never the source of truth.
  - **Named palettes** save/load to `localStorage` (`SAVED_KEY`, `listThemes`/`saveTheme`/`deleteTheme`), listed with a 4-swatch strip. Every read goes through `normalizeTheme(raw, base)`, which reconciles a stored palette against the *current* `THEME_VARS` — fills vars added since it was saved, drops retired ones, falls back on junk. Load it back raw and a palette written before `--raised` existed (or one still carrying `--border`) would apply a broken `:root`; the var list has already churned twice. Pure coverage `web/theme.test.ts`.
- **Command builder:** `./` key-bar button opens `CommandBuilder`. Lists recent/frequent (from the DB command log), cwd executables, then aliases/common/full-`$PATH` (server `GET /api/commands?cwd=` — auth'd, cwd must be a known folder). Picking a plain command then filters static subcommand/flag suggestions from `commandCatalog.ts` (free-text for unknown commands); picking a recent/frequent entry (a whole command line) inserts it directly. **Inserts** the assembled line into the PTY without a trailing newline — user reviews and presses Enter.
- **Recent/frequent commands:** sourced from the DB `commands` log (every command run in a Terminal session, with its cwd — see shell integration), not shell-history files. `recentCommands`/`frequentCommands` in `db.ts` rank distinct commands with the requested cwd preferred (same-cwd first, then global). Still filtered per-cwd in `listCommands`: only relative-path invocations (`./x`) are cwd-dependent and dropped if absent from the folder; plain names and absolute paths always kept. Ranked pool is larger than shown so the filter can still fill `HISTORY_LIMIT`. Cold-start: empty until commands are run through a Terminal session.
- **Shell integration / session events:** the `terminal` adapter (`adapters/shell.ts`) detects zsh/bash from the configured command and injects a startup script (zsh via hijacked `ZDOTDIR`+`USER_ZDOTDIR` → `shell-integration/zdotdir/`; bash via `--rcfile shell-integration/bash-rc.sh`) that still sources the user's own rc, then emits VS Code **OSC 633** markers (`E`=command line, `C`=exec, `D;code`=done, `P;Cwd=`=cwd). The adapter's `createEventParser()` strips those markers from the PTY stream and yields `SessionEvent`s; `manager.ts` updates `SessionInfo.cwd` (display/logging only — never re-parents the session, see above) and `SessionInfo.currentCommand` (set on `command-start`, cleared on `command-end`; shown in the UI session list with a pulsing dot) live and fans events to listeners (`onEvent`). Other harnesses (claude/pi) and non-zsh/bash shells get no parser — they stream raw, unchanged. Adding event support to a harness = give its adapter a `createEventParser`; keep the OSC knowledge in the adapter. Command logging lives in a single server-global `manager.subscribe` in `index.ts` (NOT the per-connection one, or every browser double-records).
- **Dynamic arg resolvers:** a catalog `ArgNode.source` names a server-side resolver (`RESOLVERS` in `commands.ts`) that runs a *fixed* command and returns live suggestions (e.g. `docker logs` → container names from `docker ps -a`; `git checkout` → branches; `npm run` → package.json scripts). Client calls `GET /api/resolve?id=&cwd=` with only the resolver **id** (never a command) — auth'd + folder-allowlisted; results cached 3s; failures degrade to free-text. Add a resolver = add an entry to `RESOLVERS` + set `source` on the catalog node.
- **Mobile keyboard:** `App.tsx` sizes `.app` to `visualViewport.height` when the keyboard is up and floats the key-bar above it; `index.html` sets `interactive-widget=resizes-content`. Together these stop the page being panned under the keyboard — don't revert without re-checking that.
- **Authentication:** the whole app is login-gated. `server/auth.ts` owns all of it — scrypt password hashing (`salt:hash`), server-side session tokens stored in SQLite (`users`/`auth_sessions` in `db.ts`) and set as an **HttpOnly cookie** (never exposed to page JS), plus the HTTP auth routes. The rest of the server only asks "who is this request?" via `authedUser()`; every `/api` route and the `/ws` upgrade are gated on it. `web/Login.tsx` is the login/signup gate and `web/auth.ts` the client helpers. Keep auth concerns in `auth.ts` — the rest of the code stays auth-agnostic.
- **LLM assist / AI-assistant mode (optional):** `server/llm.ts` talks to an **OpenAI-compatible endpoint** (`config.json` `llm` block; default local vLLM at `http://localhost:8000/v1`) to auto-answer chat `ui-request`s on the user's behalf — permission prompts (`kind:"select"`/`"confirm"` → allow/deny with a terse reason) and AskUserQuestion dialogs (`kind:"questions"` → pick option labels). Everything is **best-effort/fail-safe**: it polls the endpoint's `/models` for health, and any error/unreachable endpoint degrades to "unavailable" so the UI falls back to the normal manual flow. `server/llm.ts` (`evaluate`) is the pure, stateless judge; the mode itself is a **backend, per-session toggle** so it keeps running with **no browser open** (an unattended session doesn't stall):
  - **State:** `AssistantSettings` lives in each session's `ChatState` (`shared/protocol.ts`), toggled via the `set-assistant` `ChatAction` (handled by `manager.ts` itself, harness-agnostic — never the adapter) and folded by the reducer (`assistant-config` event); it's snapshotted on connect and synced to every client. **It's a checklist of independent capabilities**, each an `AssistantCapability` (`enabled` + its own free-text `instructions`, so they don't fight over one box): `permissions`, `questions` (+`onlyIfSure`), `autoPr` (+`autoMerge`). `enabled` is a **derived** master switch — `deriveAssistantEnabled` (`shared/chat.ts`), recomputed by `manager.chatAction` on every `set-assistant` and **never trusted from a client**, so it can't drift from the checklist. `assistantNeedsLlm` (also `shared/chat.ts`) is the companion: questions always need the endpoint, permissions need it unless blanket-accept, auto-PR never does — it drives the header button's colour and the dialog's unavailable-endpoint warning.
  - **Dialog (`web/App.tsx`, inline JSX):** the header robot button **always opens** the dialog (it no longer one-click disables — with several capabilities, editing them and "Run now" must stay reachable while the assistant is on; turning everything off is unticking the boxes). One `.assistant-section` per capability: a **bare checkbox** (enable/disable) beside a **separate `<button>`** carrying the label + chevron that toggles *only* the collapsible body — deliberately not a wrapping `<label>`, so the text can never flip the switch. Ticking auto-expands, unticking auto-collapses. **There is no Save button**: checkbox changes push `set-assistant` immediately, instruction textareas debounce 300ms (flushed on close / "Run now"), and `assistantDraft` stays authoritative while open so an echo can't fight the caret. Sections take **no fill** — the dialog ladder is already `--bg`→`--panel`→`--raised` with no fourth step, so they group by spacing + the `[data-on]` accent tint and their `--raised` controls still rise (see the elevation rules below).
  - **Decider:** `server/assistant.ts` (`attachAssistant(manager)`, wired in `index.ts`) is a server-global subscriber and the **sole** evaluator: on a `ui-request` for an enabled+capable session it calls `evaluate()`, **broadcasts** the verdict as an `assistant-decision` event (`AssistantDecision` in `ChatState.autoDecisions`), then after the same grace delay the UI used (2–10s, scaled by card size) **applies** it via `manager.chatAction(ui-response)`. So the countdown ring renders identically in the browser, but the backend owns the timer/apply — closing the tab doesn't change the outcome. It passes the *matching* capability's instructions (`permissions` vs `questions`), plus `onlyIfSure` → `llm.ts` swaps `QUESTIONS_SYSTEM` for the stricter `QUESTIONS_SURE_SYSTEM` (both built from a shared `QUESTIONS_BASE` so they can't drift), and traces the system prompt actually sent.
  - **Intervention:** any card interaction sends `cancel-assistant` (→ `assistant-decision-cleared`, which the decider observes to cancel its timer) so a manual response wins; answering the card (→ `ui-request-done`) likewise cancels. `deny` never auto-acts (surfaced for a human, prefilled reason); `plan`/`input` are never auto-answered.
  - **Visibility (trace bubbles):** whenever the LLM is queried about a card, `evaluate()` returns a `trace` (`LlmDecision.trace` = the `SYSTEM`/`USER` prompt sent + the model's `reasoning_content` thoughts + raw response); the decider posts it via `manager.postAssistantTrace` → `assistant-trace` event → `ChatState.assistantTraces` (capped 20, reducer-folded). The reducer anchors each trace to the assistant turn it explains (`anchorMessageId` = the streaming message when the card fired — where the tool call lives; survives the streaming→finalized handoff, so it's clock-independent). `ChatView` renders each as a collapsible AI-mode bubble (robot glyph + one-line `summary`, expandable Prompt/Thoughts/Response) **inline right after its anchor turn** (orphaned traces whose turn was capped out fall back to the end). Emitted for **every** deliberation incl. abstain/endpoint-error, so both allow and deny outcomes are auditable. Diagnostic/transient — not a `ChatMessage`, so it skips the render-log/resume; harness-agnostic (`AssistantTrace` in `shared/protocol.ts`). **The same array also carries plain AI-mode *notes*** from backend capabilities that consulted no LLM (`kind:"auto-pr"`, `outcome:"note"`, synthetic `requestId`, no `prompt`/`response`) — reusing it buys anchoring, capping, rewind-pruning and the orphan flush for free, at the cost of sharing the 20-entry cap. `AssistantTraceBubble` gates its disclosure on having any of prompt/thoughts/response, so a note renders as a non-expandable one-liner.
  - **Blanket-accept ("allow everything"):** when the session's `assistant.permissions.instructions` are exactly the sentinel `ALLOW_EVERYTHING` (`shared/chat.ts` `isAllowEverything`, case/trailing-punctuation tolerant), permission cards (`select`/`confirm`) skip `evaluate()` entirely and are auto-accepted — same grace-window countdown, same broadcast `assistant-decision`, same trace bubble (posted with a synthetic prompt/response noting no LLM was consulted), so the UX is identical. Needs no endpoint (`llmStatus()` gate is skipped); `questions` still go through the LLM; `plan`/`input` remain human-driven. The UI exposes it as an "allow everything" checkbox on the Instructions label row of the assistant dialog, which just writes/clears the sentinel — so typing the phrase yourself works identically (intentional). Pure coverage in `shared/chat.test.ts`; live coverage in `server/adapters/claude-assistant-allow-all.e2e.test.ts`, which **never starts the LLM poll** — on the normal path the decider bails on the `llmStatus()` gate, so a card auto-accepted there can only have come from the bypass (verified by mutation: disabling it hangs the turn).
  - **Auto PR (`server/autopr.ts` + `server/prAgent.ts` + `server/git.ts`):** the second capability. `attachAutoPr(manager, config.autoPr)` is a server-global subscriber (wired in `index.ts` beside `attachAssistant`/`attachSuggestions`) that runs the PR flow when a session's turn settles — the same `busy:false` hook `suggestions.ts` uses, gated by the pure `shouldRunAutoPr(state)` (capability on, idle, no pending card / queued prompt, a real exchange happened) — or on demand from the dialog's "Run now". A per-session single-flight `Set` (spanning the whole async flow) stops a settle and a "Run now" opening two PRs for one turn. **"Run now" travels as a `{type:"run-auto-pr"}` `ChatAction` observed via the `SessionListener.onChatAction?` hook** — *not* a no-op `ChatEvent`: `ChatEvent` means "renderable state changed" and `applyChatEvent` is the total pure function both sides run, so an inert event would smuggle an RPC onto the state-sync bus and ship dead bytes to every client. `manager.chatAction` fans the action to listeners and returns early for `run-auto-pr` so no adapter ever sees it (same "harness-agnostic actions never reach the adapter" rule as `set-assistant`/`set-draft`). A WS-layer special-case in `index.ts` would be wrong too — the `prompt`-images one exists only because image resolution is per-connection auth-scoped, and `chatAction` is called from the backend as well.
    - **The flow** (in `manager.sessionFolder(sessionId)`, each step narrating itself into the origin session's transcript as an AI-mode note): **1. branch** — only when on the integration branch: `llm.ts` `suggestBranchName(workingDiff)` → `git.ts` `sanitizeBranchName` → `<prefix>/<slug>`, deduped with a `-2`/`-3` suffix. **2. commit** — `git add -A` then up to 3 `suggestCommitMessage(stagedDiff)` attempts (each rejection fed back so the retry doesn't repeat it), validated by `sanitizeCommitMessage`, falling back to `auto-pr: update N files`. **3. push** — `git push -u origin <branch>`. **4. PR** — `prAgent.ts`. **5. merge** and **6. back to main** (`git checkout <base>` + `git pull --ff-only`) run **only when `autoMerge` is ticked**; merge is `gh pr merge <n> --squash --delete-branch`. The pure `decideFlow({dirty,onMain,diffVsBase})` picks between `commit` / `pr-only` (clean branch that already diverges — push + PR, no new commit) / `nothing` (clean and matching the base — skip to step 6 regardless of `autoMerge`).
    - **Commits are made with `-c commit.gpgsign=false`.** Signing is *interactive* (`~/scripts/git-helper.sh` has a whole `prime_yubikey_auth` for it); headless it would hang forever, wedging the flow. Same reason `git.ts` sets `GIT_TERMINAL_PROMPT=0` on every invocation.
    - **`server/git.ts`** is the git/gh boundary: never-throwing `git()`/`gh()` wrappers (cwd-scoped, timed out) plus the **pure, tested** sanitizers the LLM output must survive — `derivePrefix` (ported from git-helper's `get_branch_prefix`: NFKD-decompose → drop `\p{M}` → first word → strip to `[a-z0-9._-]`, so `Jöran` → `joran`; falls back to the email local-part, then the OS user), `sanitizeBranchName` (lowercase, everything outside `[a-z0-9]` becomes a `-`, collapsed/trimmed, capped at 40 chars on a word boundary, `null` when nothing survives), `sanitizeCommitMessage` (`null` unless a single line ≤72 chars), `fallbackSlug`. `mainBranch` defers to `origin/HEAD` before guessing main/master. The LLM is **never trusted directly** — every generated name/message is sanitized or rejected, and an unavailable endpoint just falls through to the deterministic fallbacks (steps 1–3 still work with the LLM down; step 4 can't, and reports).
    - **The PR itself is drafted by a REAL chat session** (`prAgent.ts` `runPrSession`): `manager.start("pi", {cwd: folder})` — a normal, visible tab the user can watch or take over — prompted with `/pr` (both configurable via `config.json` `autoPr: {harness, command}`, so no harness id is hardcoded in the core). It speaks only `ChatAction`/`ChatState`, never pi's wire format. Its **permission cards are handled by turning blanket-accept assistant mode on for that session** (`set-assistant` with `permissions.instructions = ALLOW_EVERYTHING`) — reusing `assistant.ts` wholesale instead of adding a second card handler — and its `autoPr` is explicitly left off so the PR session can never open a PR about itself. Its **prose** questions ("does this description look good?") are answered by `llm.ts` `supervisePr(transcript)`, which reads the same `buildSuggestionTranscript` render and returns either a reply to send or `done` + the PR number/URL. Bounded by `MAX_PR_TURNS`/`MAX_RUN_MS`/`TURN_TIMEOUT_MS`; on success the session is stopped (its exited tab keeps the transcript), on any bound/failure it's deliberately **left open for a human**.
    - **A turn ends on a `busy:true` → `busy:false` *transition*, not any `busy:false`** — pi emits several per turn (agent_end, then settled), and a naive edge match lets a stray one instantly settle the *next* prompt. (`PiDriver` in the testkit gets away with the naive form only because a test awaits between turns.)
    - Known interaction: pi's `/pr` skill writes a `pr-description.md` into the working tree, which the *next* auto-PR run will happily commit. Not special-cased — hardcoding a harness skill's filename in harness-agnostic code is the wrong trade.

The conservative default (no user instructions) allows trivially-safe read-only operations **plus file edits/writes whose target path is inside the session's workspace folder or a subfolder, or under `/tmp/`** (`LlmEvaluateRequest.workspace` = `manager.sessionFolder`); writes outside the workspace and not under `/tmp/`, `..` escapes (to non-`/tmp/`), and destructive/networked shell ops are still denied. - **Synthesized next-prompt suggestions (`server/suggestions.ts`, built):** harness-agnostic generator for chat harnesses that *don't* emit their own follow-up (pi + future ones — Claude does, so it's skipped via `HarnessAdapter.nativePromptSuggestions:true`). ## What this is

- Harness-agnostic web remote for AI coding agents.
- Single webpage to manage local agent sessions: Claude Code + pi first, other CLI harnesses later.
- User-facing overview: `README.md`.

## Architecture (settled)

- **Frontend:** React + Vite. Renders sessions, streams output, sends input back.
- **Backend:** Node. Spawns each agent as a **local subprocess in a PTY** (`node-pty`), supervises lifecycle, streams raw terminal I/O to the browser via WebSocket.
- **Terminal:** browser renders sessions with **xterm.js**; keystrokes/resize go back over `/ws`. One persistent xterm per session (hidden when inactive) so scrollback survives tab switches.
- **Single port:** UI, `/api`, and `/ws` all listen on one port (default 4000). Dev embeds Vite in **middleware mode** in the Node server (`--dev` flag, not env); prod serves `dist/web`. `/ws` and Vite HMR coexist via `noServer` + manual `upgrade` routing.
- **Harness adapters:** core abstraction. An adapter describes *how to invoke* an agent (`HarnessInvocation`: command/args/env) plus optionally how to translate its protocol (`createEventParser` for PTY event markers, `createChatTranslator` for chat sessions); all process/streaming/lifecycle is harness-agnostic in `sessions/manager.ts`.
- **Hard constraint:** keep harness-specific logic confined to adapters. UI/session-mgmt/LLM features stay harness-agnostic. New agent = new adapter, never UI/core changes. Leakage into shared code = design smell.

## Config

- No env variables. All config lives in `config.json` (gitignored).
- `config-gen.sh` runs a setup dialog to generate `config.json`. Shape in `config.example.json`.
- Keys: `harnesses` (per-harness `enabled`/`command`, optional `env` for the process — used by `claudeLocal`), `llm` (`provider`/`baseUrl`/`model` for the optional LLM assist — see above), `autoPr` (optional `harness`/`command` for the auto-PR session, default `pi` + `/pr`), `server.port`.
- Never reintroduce `process.env`-style config or `.env` files.

## LLM features

- **Built:** AI-assistant mode — auto-answering chat permission/question dialogs, synthesized next-prompt suggestions, and auto-PR (LLM-written branch name / commit message, plus supervision of the headless PR session) via an OpenAI-compatible endpoint (`server/llm.ts`; see the LLM-assist bullet in Layout).
- **Planned (not built):** session summaries, natural-language task routing, notification/triage.
- All layered on the harness-agnostic core; consume the common session interface; must not depend on a specific harness.
